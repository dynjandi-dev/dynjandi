# Internationalization (i18n)

## Core Rules

- Use **Lingui** unless the stack already has a better-integrated i18n library — see [Choosing a Library](#choosing-a-library)
- Never build a hand-rolled object-based translation layer (`strings[lang].checkout.title`) — see [DO NOT](#do-not)
- Source text is the message — write translatable copy inline in the component, not in a key registry elsewhere
- Catalogs are generated by extraction, never hand-maintained
- Compiled catalogs are build output — generate them in CI, do not commit them
- Pluralization, gender, and number/date formatting go through ICU MessageFormat, never through `if` branches in the component
- Introduce i18n before the second locale is needed, not after — retrofitting touches every string in the codebase

## Preferred Library

Use [**Lingui**](https://lingui.dev) for React, React Native, Node, and plain TypeScript projects.

It is the default because it is the only option that keeps the source readable:

- **Messages stay in the source.** `<Trans>Items in your cart</Trans>` is the message *and* its own ID. There is no key to invent, no key to keep in sync, and the component still reads as English.
- **Extraction is automated.** `lingui extract` walks the source and writes the catalogs. A new string cannot be forgotten, because nobody adds it by hand.
- **ICU MessageFormat is enforced at build time.** Macros expand to validated ICU, so a malformed plural is a build error rather than a runtime string.
- **Small runtime.** ~3 kB, and the compiled catalogs carry only the active locale.
- **Framework-agnostic.** The same catalogs serve a React frontend and a Node backend.

## Choosing a Library

**Lingui is the default, not a mandate.** A library that the framework already integrates with usually wins — it will handle routing, server rendering, and locale negotiation that would otherwise be hand-written around Lingui.

| Stack | Use | Why |
|---|---|---|
| React (Vite, CRA, SPA) | **Lingui** | The default. Nothing in the stack competes. |
| React Native / Expo | **Lingui** | Works unchanged; the macro build step fits the Metro pipeline. |
| Node / backend / CLI | **Lingui** (`@lingui/core` only) | No React dependency needed for catalogs and formatting. |
| TanStack Start | **Lingui** | No first-party i18n; Lingui's provider sits above the router. |
| **Next.js (App Router)** | **`next-intl`** | Owns locale routing, middleware negotiation, and per-request server config. Lingui works here, but you reimplement all three. |
| Remix / React Router framework mode | **`remix-i18next`** | Hooks into the loader and route lifecycle Lingui does not see. |
| Astro | **`astro-i18n`** or built-in i18n routing | Page-level routing is the whole problem; Astro already solves it. |
| Vue / Nuxt | **`vue-i18n`** / **`@nuxtjs/i18n`** | Framework-native; Lingui is React-oriented. |
| Existing codebase already on `i18next` / `react-intl` | **Leave it** | A working i18n layer is not worth a migration. Extend it. |

**Before choosing anything other than Lingui, state the reason in the PR or plan** — one sentence naming what the framework-native library handles that Lingui would not. "It's more popular" is not a reason.

Whatever you pick, it must satisfy the non-negotiables:

- ICU MessageFormat (or equivalent) for plurals, selects, and number/date formatting
- Extraction tooling — no hand-maintained catalogs
- Type-safe message access, or validated keys
- Lazy-loaded per-locale catalogs

A library failing any of these is not an alternative to Lingui. It is the hand-rolled approach with a package name.

## Lingui Setup

Configuration lives in `lingui.config.ts`:

```ts
import { defineConfig } from "@lingui/cli";

export default defineConfig({
  sourceLocale: "en",
  locales: ["en", "is", "de"],
  catalogs: [
    {
      path: "<rootDir>/src/locales/{locale}/messages",
      include: ["src"],
    },
  ],
});
```

Macros are expanded at build time, so register the compiler plugin — `@lingui/babel-plugin-lingui-macro` for Babel, `@lingui/swc-plugin` for SWC/Next.js. Without it, the macros do not resolve.

Load and activate a catalog, then wrap the tree:

```tsx
import { i18n } from "@lingui/core";
import { I18nProvider } from "@lingui/react";

export async function activateLocale(locale: string) {
  const { messages } = await import(`./locales/${locale}/messages.po`);
  i18n.loadAndActivate({ locale, messages });
}

export function App() {
  return (
    <I18nProvider i18n={i18n}>
      <Routes />
    </I18nProvider>
  );
}
```

Import macros from the per-package entry points — `@lingui/core/macro` and `@lingui/react/macro`. The old `@lingui/macro` package is deprecated, and `babel-plugin-macros` is no longer the mechanism.

## Lingui Usage

`Trans` for anything rendered as JSX; the `t` from `useLingui` for strings that are not — attributes, `aria-label`, document titles:

```tsx
import { Trans, Plural, useLingui } from "@lingui/react/macro";
import { ph } from "@lingui/core/macro";

interface CartSummaryProps {
  itemCount: number;
  customerName: string;
}

export function CartSummary({ itemCount, customerName }: CartSummaryProps) {
  const { t } = useLingui();

  return (
    <section aria-label={t`Cart summary`}>
      <h2>
        <Trans>Your cart</Trans>
      </h2>

      {/* Markup inside a message is fine — it survives translation */}
      <p>
        <Trans>
          Welcome back, {ph({ customerName })}. Review your items before{" "}
          <a href="/checkout">checkout</a>.
        </Trans>
      </p>

      {/* ICU plurals — not an if/else in the component */}
      <Plural value={itemCount} one="# item in your cart" other="# items in your cart" />
    </section>
  );
}
```

Use `ph()` to name placeholders. `{user.name}` extracts as an opaque `{0}`, which tells a translator nothing.

**Never call `t` at module level.** The macro resolves once, at import time, against whatever locale was active — so the string freezes and never updates on a locale change. Define the message and translate it at render:

```ts
import { msg } from "@lingui/core/macro";
import { i18n } from "@lingui/core";

// ✅ A message definition, not a string
const STATUS_LABELS = {
  pending: msg`Awaiting payment`,
  shipped: msg`On its way`,
  delivered: msg`Delivered`,
} as const;

// Translated where it is rendered
export function statusLabel(status: keyof typeof STATUS_LABELS): string {
  return i18n._(STATUS_LABELS[status]);
}
```

In React Server Components, call `setI18n` from `@lingui/react/server` in every page and layout; `Trans` and `useLingui` from `@lingui/react/macro` then work on both sides of the boundary.

## Workflow

```bash
lingui extract              # source → PO catalogs (run after adding or changing copy)
lingui compile --typescript # PO → runtime catalogs with types (run before build)
```

```json
{
  "scripts": {
    "i18n:extract": "lingui extract",
    "i18n:compile": "lingui compile --typescript",
    "build": "npm run i18n:compile && vite build"
  }
}
```

- **Translators edit the `.po` files.** Those are source and are committed.
- **Compiled catalogs are build output.** Gitignore them and generate them in the build.
- **`lingui extract` in CI should be clean.** A diff means someone added copy without extracting — fail the job.

## Formatting Numbers, Dates, and Currency

Format through the i18n layer or `Intl`, never with string concatenation. A locale is not only a language — `1,234.56` and `1.234,56` are the same number.

```tsx
import { useLingui } from "@lingui/react/macro";

const { i18n } = useLingui();
i18n.number(1234.56, { style: "currency", currency: "EUR" });
i18n.date(invoice.dueDate, { dateStyle: "medium" });
```

For date and time values, the type you format matters as much as the locale — see [`dates.md`](dates.md).

## DO NOT

- **Hand-roll an object-based translation layer.** This is the single thing this document exists to prevent:

  ```ts
  // ✖️ NEVER
  const strings = {
    en: { cart: { title: "Your cart", empty: "Your cart is empty" } },
    is: { cart: { title: "Innkaupakarfan þín", empty: "Karfan er tóm" } },
  };
  const t = (key: string) => key.split(".").reduce((o, k) => o?.[k], strings[lang]);

  <h2>{t("cart.title")}</h2>
  ```

  Every failure mode at once: the component no longer says what it renders, so you cannot read the UI from the code or review a copy change. `t("cart.title")` is unverifiable — a typo is `undefined` at runtime, in production, in one locale. Nothing enforces that locales stay in sync, so a missing `is` key is silent. Plurals and gender become `if` branches. There is no extraction, so adding a string means editing every locale by hand and forgetting one. Switching to a real library later means rewriting every call site.

- Use `t("some.key")`-style indirection at all, in any library, where the source text could be the message. The key registry is the readability problem; `i18next` with keys is only marginally better than the object above.
- Concatenate translated fragments — `t("Hello") + " " + name` produces word order no translator can fix. Interpolate inside one message.
- Branch on count or gender in the component instead of using ICU plural/select.
- Put a locale in React state or a context separate from the i18n provider — two sources of truth drift.
- Hardcode a string "temporarily". It stays, and extraction will not find it.
- Commit compiled catalogs, or hand-edit them.
- Use the deprecated `@lingui/macro` package, or rely on `babel-plugin-macros`.
- Default a missing translation to the raw key. Fall back to the source locale.
- Translate log messages, error codes, or anything machine-read. Only user-facing copy.

## PRIORITY

```
Framework-native library > Lingui > any other library > hand-rolled
Source text as message > key registry
Extracted catalogs > hand-maintained catalogs
ICU MessageFormat > conditional logic in components
```
